Why Twigg

Twigg was born out of a belief that the version control most of the industry uses is inefficient. Git was made for distributed development: no authoritative server, patches sent over email, every clone carrying the full history. Most teams work in one centralized codebase instead, and pay for that flexibility in complexity.

Big tech's internal tooling is centralized, far more efficient and much simpler to use. Twigg brings that to everyone, built on how we believe software should be developed:

  • Trunk-based development, not long-lived branches
  • Small increments, each one reviewed and tested on its own
  • A monorepo, with clear ownership of every directory

It's written from scratch, combining the best ideas from other version control systems:

  • Mercurial: delta compression and commit obsolescence
  • Git: Merkle trees
  • Fossil: a single binary with integrated tools
  • Google's Critique and Meta's Phabricator: stacked code review and stable commit ids like c/123

Features

tw commit

Version control

Stacked commits with versions. Amend any commit and everything on top of it is rebased. No branches, no staging area.

twigg → git

Git mirror

Twigg works on top of your existing Git repository: every submitted commit is pushed to it, so deploys, CI and anything else that reads from Git keep working. Adopt Twigg gradually, or leave anytime.

c/67v1 ↔ c/67v2

Code review

Every commit is reviewed on its own, version by version, with OWNERS files declaring who owns each directory.

CI.json · CD.json

CI/CD

Jobs live in the repo next to the code they test and only run when their folder changes. Unlimited minutes.

b/12

Issue tracker

Bugs and feature requests live next to the code, linked to the commits that fix them.

tw bug-get b/12

API for agents

The CLI is backed by the server's API, so agents can do what you do: read bugs, set review descriptions, etc. It ships a skill that teaches them how, and more of the API is on the way.
